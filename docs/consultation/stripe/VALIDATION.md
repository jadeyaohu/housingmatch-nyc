## Security review conclusions and limits

No public UUID-only Checkout/refund/confirmation path exists. Staff identity is verified by Supabase Auth and independently checked against admins inside the privileged SQL operation. Invitation status is a limited bearer capability, not identity proof. Tokens stay in a URL fragment initially, then memory and HttpOnly per-attempt cookies; only hashes are stored in the DB. Non-secret attempt selectors cannot authorize without a matching cookie. The per-attempt design fixes cross-tab attribution when multiple invitations are open. Referrer policy suppresses transmission of the fragment/selector on navigation and requests.

Stripe keys must use sk_test_; retrieved sessions/intents and signed events must be test objects with expected amounts, currency and associations. Webhook dedupe and state updates share a transaction. Provider responses/redirects do not set paid/refunded; only verified webhook processing does. Appointment confirmation is separate. Service credentials are server-only; no card storage, customer PII in metadata/response, analytics calls or Production settings changed.

Intentional limitations: no automated reconciliation worker, staff login UI, invitation email delivery, partial refunds, disputes/Connect support, or booking identity verification beyond the private capability. Ambiguous provider errors retain their reservation; an operator must investigate rather than delete it or create another charge. Old operations beyond 23 hours are refused instead of risking Stripe idempotency-key reuse. Status access expires with the invitation. Monitor webhook failures and manually replay genuine events after configuration recovery. Application authorization does not replace protection of service credentials and admin access.
